Выдача пачкой через `createMany(skipDuplicates)` + `createManyAndReturn` сохраняет защиту от гонок. Запросов на сохранение записи стало меньше.

## Замечания (по важности)
1. **Средняя. Защита входа обходится параллельными запросами.** `recordFailedLogin` читает `LoginAttempt` до bcrypt и пишет `failedCount + 1` через `upsert` (чтение-изменение-запись без атомарности). N одновременных запросов прочитают одно и то же состояние и запишут `1`, поэтому счётчик не дойдёт до 5, и перебор в параллель не блокируется. bcrypt cost 10 (~60–100 мс) ограничивает скорость на сервере, но не отменяет обход. Решение: атомарный `INSERT ... ON CONFLICT DO UPDATE SET "failedCount" = "failedCount" + 1` (или `increment` внутри `update`), либо повторное чтение после bcrypt, либо блокировка `pg_advisory_xact_lock` по email. Тест на параллельные попытки отсутствует (тесты используют имитацию таблицы).
2. **Средняя (известное, расширяю). Защита только по email.** Следствия: (а) любой может заблокировать чужой аккаунт на 15 минут, отправив 5 неверных паролей (отказ в обслуживании жертве, а у ребёнка или взрослого нет способа обойти); (б) перебор паролей по многим email с одним паролем не ограничен; (в) таблица `LoginAttempt` растёт записями по любым введённым email без очистки; (г) регистрация и подбор кода приглашения вообще без ограничения частоты (код 32^8 ≈ 1,1·10^12, подобрать трудно, но запросы бесплатны, а bcrypt на регистрации нагружает CPU). Для пилота допустимо; перед публичным запуском добавить ограничение по IP (заголовок `x-forwarded-for` за прокси), периодическую очистку старых строк и ограничение регистрации.
3. **Средняя. Регистрация принимает смещения вместо IANA-имён.** `timeZoneSchema` использует `normalizeTimeZone` (через `Intl`), а он принимает `+23:59`, `-23:59` (проверил в Node 24: сохраняется как есть; не «в UTC», как предполагалось; в UTC уходят только заведомо неверные значения). Пояс при регистрации не считается сменой (`timeZoneChangedAt = null`), а потом `isSupportedTimeZone` смещение отвергает, поэтому такой пользователь остаётся с `+23:59` навсегда и имеет окно «сегодня/вчера» шире любого реального пояса (до ~10 часов сверх). Накрутка баллов ограничена суточными лимитами, ущерб небольшой. README утверждает, что пояс принимается «только как IANA-имя» — для регистрации это неверно. Решение: в `timeZoneSchema` использовать `isSupportedTimeZone` (с откатом к UTC).
4. **Средняя. Первая смена пояса после регистрации ничем не ограничена** (`timeZoneChangedAt = null`). Дальше раз в 7 дней. Итого в первую неделю доступны два разных пояса; это сознательное решение (регистрация не считается сменой), но стоит зафиксировать в README как принятое.
5. **Средняя. SQL `grantAchievements` не проверен на реальной БД.** Все тесты подменяют `$queryRaw`, поэтому синтаксис и приведения типов (`::int` над `SUM`, возвращаемый тип `date`) проверены только чтением; сборка их не проверяет. Рекомендуется один раз выполнить `loadStats`/`loadLogDays` на тестовой БД (не на рабочей) и сверить с прежней логикой. Попутно: `SUM(points)::int` переполнится только на 2,1 млрд баллов, неактуально. Названия достижений в сообщении теперь идут в порядке выдачи из БД, а не в порядке каталога `ACHIEVEMENTS` (если сразу выдаётся несколько) — мелочь.
6. **Средняя. Не всё этапа 6 закоммичено.** `git status`: изменено 28 файлов и добавлено 8 новых (`login-throttle.ts`, `delete-form.tsx`, 4 теста, миграция `20261006140000_login_attempts_tz_changed`) без коммита. В репозитории нет миграции для `LoginAttempt` и `timeZoneChangedAt`, поэтому деплой с текущего коммита сломает вход. Сделать коммит (на русском, по правилам `AGENTS.md`) до деплоя.
7. **Низкая. Локальный запуск по README может использовать неверный `AUTH_URL`.** В `.env.example` стоит `https://your-domain.example`, а в README шаг запуска говорит «впишите DATABASE_URL и AUTH_SECRET» и про `AUTH_URL` не упоминает. Скопированный как есть файл подставит чужой адрес. Исправить: в `.env.example` значение `http://localhost:3000` (или закомментировать) и добавить `AUTH_URL` в шаг запуска.
8. **Низкая. Лимит 20 целей без блокировки:** две параллельные операции дадут 21-ю цель (принято, описано в README). Ущерб нулевой.
9. **Низкая. `Europe/Kyiv` в этой версии Node сохраняется как `Europe/Kiev`** (ICU), пользователь с Kyiv при регистрации получит Kiev; в списке на странице «Семья» этот пояс есть через `current`. Работает; повторный выбор Kyiv при текущем Kiev засчитается как смена (сравнение строк) и израсходует недельный лимит.
10. **Низкая. `status.md` устарел:** указывает этап 5, 662 теста, 3 миграции; замечания аудита 5 помечены как «на этап 6», хотя исправлены. Обновить.
11. **Низкая. Сборка на Vercel:** README рассчитывает на автогенерацию клиента Prisma при установке; на Vercel из-за кэша зависимостей надёжнее добавить `"postinstall": "prisma generate"` (или `prisma generate && next build`).
12. **Низкая, из прошлых аудитов, не закрыто и описано в README:** только 30 последних записей в списках; записи с 0 баллов учитываются в «первых» достижениях и серии; `PointsEvent.date` может быть NULL; нет интеграционного теста изоляции семей на реальной БД; нет восстановления пароля и подтверждения email; у «профиля» члена семьи только имя и роль; смена роли и исключение из семьи отсутствуют.
