# Аудит: этап 4 «Геймификация» (план 01-family-wellness-mvp) и правило дат

## Итог
**Готово с замечаниями.** Критичных уязвимостей (утечки данных, межсемейного доступа, начисления за чужие записи) нет. Базовая накрутка (повторная отправка, удаление и повторное создание) закрыта. Но суточный лимит обходится двумя способами: гонкой и окном дат из 4 дней. Правило пользователя «только сегодня и вчера» на сервере не выполнено строго.

## Что соответствует цели
- **Логика в отдельном чистом модуле** `src/lib/gamification.ts` (как требует план): баллы, уровни, 10 достижений, серии. Покрыта тестами.
- **Баллы.** Активность: 1 балл за 5 минут, максимум 60 за запись. Питание и здоровье: по 5. Вода: 1 балл за 250 мл, максимум 8. Суточные лимиты по типу (100 / 20 / 8 / 5). Максимум в день по одной дате: 133.
- **Уровни.** `floor(sqrt(p/50)) + 1`: уровни 2, 3, 4, 5 на 50, 200, 450, 800 баллов. Границы целые (`50·n²/50` точно), ошибок округления нет. `levelProgress` не делит на ноль, процент ограничен 0..100.
- **Транзакции.** Запись, `PointsEvent` и достижения создаются в одном `$transaction`. Ошибка откатывает всё (тест есть). Удаление записи и отзыв её баллов — тоже в одной транзакции.
- **Дубли и повторная отправка.** `@@unique([sourceType, sourceId])` не даёт начислить дважды за одну запись. Повторная отправка формы создаёт новую запись, но её баллы всё равно режет суточный лимит.
- **Удаление и повторное создание.** Лимит считается по оставшимся `PointsEvent`, а не по счётчику. После удаления баллы удаляются вместе с записью, поэтому «удалить и создать заново» не даёт больше лимита. Проверено разбором сценариев: сумма за день не превышает лимит. Событие с 0 баллов создаётся тоже, так что уникальность работает и для записей сверх лимита.
- **Изоляция по семье.** `/progress`: `requireUser()`, `familyId` из БД по сессии, `groupBy` с `where: { user: { familyId } }`. Участники берутся из `me.family.users`. Достижения показываются только свои (`userId: me.id`). Email и хеш не выбираются.
- **Начисление и удаление только для себя.** `userId` берётся из сессии. В `deleteMany` и `revokePoints` стоит `userId`, чужие события не затрагиваются.
- **Миграция.** `20261006120000_points_source_unique`: добавляет `date`, индекс `(userId, sourceType, date)` и уникальный индекс. Соответствует `schema.prisma`. `migrate status` показывает актуальную схему, ручное написание не ломает историю (имя и порядок корректны).
- **Нет утечки секретов.** `.env` не читал. В коде секретов нет, ошибки БД уходят только в `console.error`.
- **Закрыто замечание аудита 3 о нижней границе даты** (окно ограничено).

## Замечания (по важности)
1. **Средняя. Окно дат на сервере — 4 дня, а не 2.** `logDate` допускает от UTC-сегодня −2 до +1 (позавчера, вчера, сегодня, завтра). Решение пользователя: только сегодня и вчера. Последствия для геймификации:
   - Суточные лимиты действуют по дате записи, поэтому за один сеанс можно собрать лимиты 4 дат: до 4×133 = 532 баллов вместо 266 (при законных двух датах). Подделать запрос (минуя форму с `min/max`) просто.
   - Серию «3 дня» можно получить сразу: записи на D−2, D−1, D, D+1 образуют 4 дня подряд. Серию «7 дней» можно получить за 4 дня использования, записывая каждый день на «завтра» вперёд.
   Причина осознанная (часовые пояса), но она приводит к обходу правила. Решение: хранить часовой пояс пользователя (поле в `User` или cookie, переданное формой, например смещение в минутах, проверенное в диапазоне −12..+14 ч) и вычислять «сегодня/вчера» на сервере точно. Минимум: принять окно D−1..D+1 для расчёта по UTC+смещению, а для серий и баллов не засчитывать даты, которых ещё нет в UTC.
2. **Средняя. Гонка при параллельных запросах обходит суточный лимит** (известно). Транзакция идёт на уровне READ COMMITTED: две параллельные транзакции читают одну и ту же сумму `earnedToday`, обе начисляют. Уникальность (sourceType, sourceId) здесь не помогает. Ограничено только скоростью запросов. Решение: заблокировать строку пользователя в начале транзакции (`SELECT ... FOR UPDATE` через `$queryRaw` или `pg_advisory_xact_lock(hash(userId))`) либо `isolationLevel: Serializable` с повтором при P2034. Теста на гонку нет.
3. **Средняя. Достижения не отзываются, а баллы отзываются** (известно). Можно набрать 100/500/1000 баллов или 5-й уровень, удалить записи и сохранить достижение. Для «первых» достижений и серий это допустимо. Для достижений по баллам и уровню — расхождение с отображаемыми баллами на `/progress` (достижение за 1000 при 0 баллов). Решение: оставить как «заслуженное навсегда» и явно написать это в плане и UI, либо отзывать при удалении. В любом случае зафиксировать решение. Тест (`достижения при удалении не отзываются`) фиксирует текущее поведение, это хорошо.
4. **Средняя. Удаление записи не пересчитывает баллы более поздних записей за день** (известно). Пример: вода A получила 8, B получила 0 (лимит). Удаляем A: сумма 0, B остаётся с 0 баллов, пользователь потерял баллы за запись, которую честно сделал. Накрутки это не даёт (повторное создание не превышает лимит), но честного пользователя «наказывает». Решение: после удаления пересчитывать события за (userId, kind, date) в порядке `createdAt`, либо считать баллы из записей на лету.
5. **Низкая. Одиночная запись может породить ошибку 500 при гонке достижений.** `userAchievement.create` и `achievement.upsert` без обработки P2002 при параллельных запросах: транзакция откатится (запись пропадёт), пользователь увидит общее сообщение об ошибке. Данные целы. Решение: `createMany({ skipDuplicates: true })` или блокировка из пункта 2.
6. **Низкая. Нулевые записи дают достижения и серии.** Запись «активность 1 минута» (0 баллов) или приём пищи с описанием «а» засчитываются в «первую активность» и серию дней. Это допустимо для MVP, но стоит учесть: серии не защищены от пустых записей. Можно требовать минимум баллов для засчёта серии.
7. **Низкая. Каждое сохранение выполняет ~10 запросов в транзакции** (counts, `distinct date` по всем записям пользователя, `userAchievement`). Для MVP ок. Со временем выборка `distinct date` по всем записям будет расти. Позже можно хранить серию/счётчики или ограничить выборку последними 7+ днями. Таймаут интерактивной транзакции Prisma по умолчанию 5 с.
8. **Низкая. `PointsEvent.date` и `sourceType` допускают NULL.** Старые события без даты не учитываются в лимите. Новые всегда с датой. Данных до этапа 4 нет, но колонку можно сделать обязательной в следующей миграции.
9. **Низкая. Ручная миграция.** Допустима, схема совпадает с БД (`migrate status` чист). Рекомендую при первом доступе к рабочему окружению запустить `prisma migrate diff --from-migrations ... --to-schema-datamodel` и убедиться, что расхождений нет. Миграция дропает индекс `PointsEvent_userId_idx`: запросы только по `userId` (`aggregate` в `grantAchievements`) пойдут по префиксу составного индекса `(userId, sourceType, date)`, так что индекс всё равно используется.
10. **Информационно. Рейтинг семьи на `/progress` сортируется по баллам без дополнительного ключа.** При равенстве порядок не определён. Для детей в семье соревновательный рейтинг — продуктовое решение (этап 6).
11. **Информационно. Лимиты в сообщении.** При 0 баллов пользователь видит «лимит баллов на сегодня достигнут», даже если баллы за запись равны 0 по формуле (например, активность 4 минуты, вода меньше 250 мл). Сообщение вводит в заблуждение. Можно различать «лимит» и «слишком мало для баллов».
12. **Информационно. Страницы не покрыты тестами.** Фильтр семьи в `/progress` проверен чтением кода (верно). Тестов самой страницы нет, нет интеграционного теста «две семьи» (унаследовано из аудита 3).

## Результаты тестов
- `npm test`: **420 из 420**, 11 файлов (перезапустил, подтверждено).
- Покрыто: формулы баллов и граничные значения, `applyDailyLimit` (остаток, сверх лимита, отрицательные значения), уровни и границы, `levelProgress`, серии (месяц, год, 29 февраля, дубли, некорректные даты), каталог достижений, транзакции (создание, откат при ошибке), нулевые события при превышении лимита, выдача достижений один раз, отзыв баллов при удалении, условие `{id, userId}`, вывод `savedMessage`.

## Рекомендации
1. Точно реализовать правило дат: передавать часовой пояс (смещение) и проверять «сегодня/вчера» на сервере. Убрать «завтра» и «позавчера». Добавить тесты на границы (замечание 1).
2. Закрыть гонку блокировкой по пользователю или Serializable с повтором, добавить тест на параллельные вызовы (замечания 2, 5).
3. Решить судьбу достижений при удалении записей (отзывать или явно оставлять) и записать в план (замечание 3).
4. Пересчитывать баллы за день после удаления либо документировать, что освободившийся лимит не возвращается (замечание 4).
5. Развести сообщения «лимит достигнут» и «слишком мало для баллов» (замечание 11).
6. Перед этапом 5 (панель семьи) добавить интеграционный сценарий «две семьи» на тестовой БД, включая `/progress`.
7. Сделать `PointsEvent.date` обязательной после проверки данных.
