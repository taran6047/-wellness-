# Аудит: этап 5 «Семейные цели и панель» (план 01-family-wellness-mvp) и правки по аудиту этапа 4

## Итог
**Готово с замечаниями.** Критичных уязвимостей нет: права на цели проверяются на сервере по данным из БД, изоляция по семье соблюдена на панели, в целях и в подсчёте прогресса. Правки по аудиту этапа 4 (часовой пояс, блокировка, `skipDuplicates`) реализованы корректно. Главные замечания: правило «сегодня и вчера» по-прежнему обходится сменой часового пояса (в ограниченном виде), `deleteGoalAction` без обработки ошибок, число запросов на панели растёт с числом целей, нет лимита на число целей. До критериев готовности из `goal.md` по функциям всё есть; не хватает этапа 6 (адаптив, безопасность, README, ручная проверка).

## Что соответствует цели
- **Цели.** Создание цели (название, метрика из 6, целевое значение, период до 366 дней), список с прогрессом, статусы «В процессе / Достигнута / Срок истёк», удаление. Пример из плана («300 км за месяц») выражается метрикой `activity_km`.
- **Панель (`/`).** Баллы семьи, рейтинг с уровнями, до 3 активных целей, последние 5 достижений семьи, быстрые ссылки. Это закрывает «на общей панели видны семейные цели и прогресс» из критериев готовности.
- **Права.** `createGoalAction` и `deleteGoalAction` вызывают `requireUser()`, роль берётся из БД при каждом вызове (не из сессии/формы), `me.role !== "adult"` — отказ до валидации. `familyId` берётся из пользователя, поле из формы игнорируется (zod отбрасывает лишние ключи, тест на подделку есть). Удаление: `deleteMany({ id, familyId })` — чужую цель удалить нельзя. UI скрывает форму и кнопку для детей, но защита не на UI. Роль «взрослый» при вступлении выбирается самостоятельно — это зафиксированное решение пользователя (status.md), права на цели от него зависят (см. замечание 6).
- **Изоляция по семье.** Панель: `groupBy` с `where: { user: { familyId } }`, достижения `where: { user: { familyId } }`, цели `where: { familyId }`, участники из `me.family.users`. `metricTotal` везде фильтрует `user: { familyId }`. В выборках нет email и хеша. Данные о здоровье (вес, сон, заметки) на панель не попадают, только счётчик записей в метрике.
- **Подсчёт прогресса.** Период включает оба конца (`gte start`, `lte end`), даты везде UTC-полночь (`logDate` и `dateInTimeZone` дают UTC-даты), сравнение с `today` тоже UTC-полночь; `daysLeft`, `expired`, `percent` (0..100, `floor`), деление на 0 исключено, отрицательные значения обрезаются. Метрика «баллы»: по `PointsEvent.date`, а для событий без даты — по `createdAt` в `[start, end+1 день)` (UTC). Условие корректно и покрыто тестом. Неизвестная метрика из БД не роняет страницу.
- **Правки по аудиту 4.**
  - Часовой пояс: `User.timeZone` (миграция `20261006130000_user_time_zone` в `migrate status`), `normalizeTimeZone` с запасным UTC, `isAllowedLogDate` проверяет ровно «сегодня» и «вчера» в поясе пользователя на сервере во всех четырёх действиях записи. Окно «завтра» и «позавчера» убрано. Форма на `/family` меняет пояс только себе (`me.id` из сессии, подделка id в форме игнорируется). Пояс при регистрации берётся из браузера.
  - Блокировка: `pg_advisory_xact_lock(hashtext(userId))` через `$executeRaw` первой операцией транзакции во всех четырёх создателях записей (раньше любых чтений суммы); замок снимается по завершении транзакции. `$executeRaw` (а не `$queryRaw`) подходит для функции, возвращающей void. Коллизия `hashtext` лишь сериализует двух пользователей, вреда нет. Тесты проверяют вызов и порядок (замок до чтения, отказ при ошибке замка).
  - Достижения: `achievement.createMany({ skipDuplicates })` и `userAchievement.createMany({ skipDuplicates })`, `granted` пополняется только при `count > 0`. Гонка достижений (замечание 5 аудита 4) закрыта.
- **Исправленные по ходу ошибки.** `timeZoneSchema` теперь необязательный (`unknown().optional().transform`), `superRefine` в `goalSchema` проверяет `instanceof Date` и не падает на неверной дате; поле с ошибкой возвращает своё сообщение.
- **Секреты.** `.env` не читался. В коде секретов нет, ошибки БД логируются через `console.error`, пользователю идёт общее сообщение. React экранирует название цели (XSS нет). Название ограничено 100 символами.

## Замечания (по важности)
1. **Средняя. Правило «сегодня и вчера» можно обойти сменой часового пояса.** Пользователь меняет пояс сам и без ограничений: сменил пояс, записал на «сегодня» в нём, вернул. Сервер принимает любую строку, которую понимает `Intl` (не только список из 28 поясов в UI), в том числе смещения `+23:59` и `-23:59` (проверил в Node 24: принимаются и сохраняются как есть). Итоговое окно для одной реальной секунды: от UTC-даты −2 до +1, то есть те же 4 даты, что и в аудите 4. Оценка ущерба: сверх лимитов суточные баллы не растут (у каждой даты свой лимит 133, каждая дата открыта ограниченное время), поэтому средняя накрутка не превышает 133 баллов в день; обход даёт только разовую «предоплату» на 1–2 дня вперёд и досрочное продвижение серии на 1–2 дня. Неточность доверия к клиенту сохраняется. Решение: ограничить частоту смены пояса (поле `timeZoneChangedAt`, например раз в 24 часа или реже) и/или принимать только IANA-имена из белого списка/`Intl.supportedValuesOf("timeZone")`, отвергая `±HH:MM`; в `isAllowedLogDate` добавить абсолютный предел по UTC (не дальше UTC-сегодня +1 и −2). Зафиксировать как принятый риск, если решение — доверять.
2. **Средняя. Число запросов на панели и странице целей растёт с числом целей, лимита на цели нет.** `getFamilyGoalsWithProgress` загружает все цели семьи, включая истёкшие и достигнутые, и на каждую делает отдельный агрегат (`Promise.all`, N запросов; на панели нужны только 3 активные цели). Оценка запросов на панели: `getCurrentUser` (user + family + users, несколько запросов Prisma), `groupBy`, `findMany` целей, N агрегатов, достижения (с join). То есть ~7 + N. Создавать цели можно без ограничений (любой взрослый, любое число): сотни целей замедлят обе страницы и создадут нагрузку на БД. Решение: ограничить число целей на семью (например, 50 активных) в `createGoalAction`; на панели считать прогресс только для активных по сроку (`endDate >= today`) и `take` перед расчётом; на `/goals` — пагинация или скрытие давно истёкших. Дополнительно обернуть `getCurrentUser` в `React.cache`, если он будет вызываться из нескольких компонентов в одном запросе (сейчас `Header` использует только `auth()` с JWT, дубля запросов к БД нет).
3. **Средняя. `deleteGoalAction` без `try/catch`.** Сбой БД в `deleteMany` приведёт к необработанному исключению (страница ошибки Next.js), в отличие от `createGoalAction`, где ошибка перехватывается и пользователю показывается общее сообщение. Для ребёнка и невалидного id функция молча выходит без сообщения. Данные при сбое не портятся (одиночная операция), поэтому уязвимости нет; это вопрос устойчивости и обратной связи. То же устройство у `deleteRecord` в `actions/logs.ts`. Решение: `try/catch` с `console.error`, возврат состояния с сообщением (через `useActionState` или `redirect` с параметром); в тестах добавить случай отказа БД.
4. **Низкая. Прогресс и статус «достигнута» вычисляются на лету, а не фиксируются.** Удаление записей (баллы отзываются, метрики уменьшаются) может вернуть «Достигнута» в «В процессе» или «Срок истёк». Для MVP допустимо, но стоит решить: фиксировать момент достижения (`achievedAt`) или документировать. Статус «Достигнута» при `current >= target` показывается и после окончания срока (это разумно).
5. **Низкая. «Сегодня» для расчёта статуса цели зависит от пояса того, кто смотрит.** Члены семьи в разных поясах в пограничные часы увидят разные `daysLeft` и «Срок истёк». Цель задаётся датами без пояса. Для семьи приемлемо; можно считать по поясу создателя семьи.
6. **Низкая. Роль «взрослый» выбирается самим пользователем при вступлении.** Ограничение «цели только взрослые» защищает от случайных действий ребёнка, но не от осознанного: ребёнок, знающий код, может вступить как взрослый или зарегистрироваться на другое имя. Решение пользователя сохранено (status.md), поэтому не дефект этапа, но формулировку в README и UI стоит сделать честной. Смена роли и исключение из семьи отсутствуют.
7. **Низкая. Нет границ дат начала и конца цели.** Допустимы любые даты формата `YYYY-MM-DD` (например, `0001-01-01`), ограничен только период (≤366 дней). Это не ломает расчёты (даты UTC), но позволяет создавать цели в далёком прошлом или будущем. Предложение: допустимое окно, например, начало не раньше −1 год, окончание не позже +2 лет.
8. **Низкая. Сумма `distanceKm` — число с плавающей точкой.** Сравнение `current >= target` может дать 99% вместо 100% из-за погрешности (например, сумма равна 0.29999999999999993 при цели 0.3). Редко; решение: сравнивать с допуском `1e-9` или хранить километры в метрах (Int).
9. **Низкая. Нет проверки на дубли целей и нет редактирования.** Можно создать несколько одинаковых целей; цель можно только удалить и создать заново (прогресс при этом не теряется, он считается по записям).
10. **Низкая. Блокировка и пул соединений.** Параллельные записи одного пользователя ждут замок, удерживая соединения (транзакция в Prisma, таймаут по умолчанию 5 с). Серия параллельных запросов от одного аккаунта может занять пул Neon. Относится к rate limiting (этап 6).
11. **Информационно. Расхождение в видимости достижений.** На `/progress` показываются только свои достижения, на панели последние достижения всей семьи (с именем). Это допустимо (данные семьи видны членам семьи), но стоит сделать единым.
12. **Информационно. `timeZoneSchema.parse` в `updateTimeZoneAction` при пустом или неверном значении молча сохраняет UTC**, перезаписывая прежний пояс. Из UI такое не отправить; вручную можно, ущерб только собственному аккаунту. Лучше вернуть ошибку, а не заменять.
13. **Информационно. `isAllowedLogDate` вызывает `dateInTimeZone` дважды** (каждый раз со своим `new Date()`): в мельчайшем окне на границе полуночи значения могут разойтись на день. Практически не проявляется.
14. **Информационно. `status.md` устарел**: указано «533 из 533» (сейчас 662) и этап 4 как текущий. Обновить после приёмки этапа 5.
15. **Информационно. Лишнего кода не найдено.** `GOAL_STATUS_LABELS`, `formatGoalValue`, `MAX_GOAL_*` используются.

- `npm run build` и `prisma migrate status` (3 миграции, актуально) — по данным заказчика, мной не перезапускались. Ручная проверка в браузере (в том числе с телефона) не выполнялась.

## Критерии готовности из goal.md: что выполнено и чего не хватает
Критерий: «Семья регистрируется и добавляет членов семьи. Каждый отмечает активность, питание и здоровье. За это начисляются баллы и уровни, открываются достижения. На общей панели видны семейные цели и прогресс.»
- Регистрация, вход, создание семьи, вступление по коду: есть (этап 2).
- Активность, питание, вода, здоровье: есть (этап 3).
- Баллы, уровни, достижения: есть (этап 4).
- Семейные цели и общая панель: есть (этап 5).
- Ограничения: рабочий проект, безопасность паролей и данных (bcrypt, изоляция по семье) — выполнено, но не завершена проверка; адаптив — только Tailwind-классы, на телефоне не проверялся.

До полного выполнения не хватает (этап 6 и долги):
1. Адаптив: проверка на экране телефона (панель, формы, навигация в шапке с `flex-wrap`, поля даты).
2. Безопасность: rate limiting входа и регистрации (отложено с этапа 2), `AUTH_URL` и `trustHost` для продакшена, заголовки безопасности, лимиты на число целей и записей, решение по перевыпуску кода приглашения; проверка «две семьи» на тестовой БД; ограничение смены часового пояса (замечание 1).
3. Расширенная проверка ввода: границы дат целей, ошибки в `deleteGoalAction`.
4. README: сейчас 21 строка (запуск есть). Добавить описание переменных окружения, миграций (`migrate deploy`), правил баллов и уровней, правила дат, прав взрослых и детей, ограничений (нет медицинских советов, нет браслетов), деплой.
5. Ручной сквозной сценарий из «Проверки» плана (регистрация, добавление члена семьи, записи, рост баллов, достижения, цели на панели) и итоговый `plans/audit-01-*.md`.
6. Обновить `status.md`.
