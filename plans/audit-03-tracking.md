# Аудит: этап 3 «Учёт» (план 01-family-wellness-mvp)

## Итог
**Готово с замечаниями.** Критичных и опасных проблем не найдено. Требование этапа выполнено: формы и списки активности, питания и воды, здоровья есть, данные семьи видны её членам. Замечания касаются UX и подготовки к этапу 4.

## Что соответствует цели
- **Три раздела учёта по goal.md.** Активность (тип, минуты, км, заметка), питание (приём пищи, описание) и вода (мл), здоровье (вес, сон, самочувствие, заметка). Ссылки есть в `header.tsx`.
- **Видимость в семье.** Все четыре `listFamily*` в `src/lib/logs.ts` фильтруют `where: { user: { familyId } }`. `familyId` берётся из `requireUser()` (сессия и БД), а не из запроса. Автор подтягивается только как `id` и `name`, без email и хеша пароля.
- **Запись только от своего имени.** `userId` берётся из сессии (`me.id`). Поля `userId` и `familyId` из FormData не читаются. Тест это проверяет.
- **Удаление только своих записей.** `deleteMany({ where: { id, userId } })`. Кнопка в UI показывается только автору (`item.authorId === meId`), но защита стоит на сервере. `id` проверяется через `recordIdSchema`.
- **Защита страниц и действий.** Каждая страница и каждое действие вызывает `requireUser()`. Без сессии идёт редирект и ничего не пишется.
- **Валидация (zod, на сервере).** Диапазоны: минуты 1–1440 (целое), км 0.01–1000, вода 1–5000 мл (целое), вес 2–500, сон 0–24, самочувствие 1–5 (целое). Тип активности и приёма пищи берутся из белых списков. Заметка и описание не длиннее 500 символов. Для здоровья нужно заполнить хотя бы одно поле. NaN и нечисловые строки отклоняются.
- **Дата.** Формат YYYY-MM-DD, невозможные даты вроде 2026-02-30 отклоняются, будущее дальше +24 часов отклоняется. Дата хранится как UTC-полночь и показывается с `timeZone: "UTC"`, поэтому день не «съезжает». Клиентский `today()` берёт локальную дату, `max` ограничивает выбор.
- **XSS.** Заметки, описания и имена выводятся как текст через JSX. `dangerouslySetInnerHTML` не используется, поэтому React экранирует вывод. Для HTML-в-заметке отдельного теста нет, но оснований для риска тоже нет.
- **Ошибки.** При сбое БД пользователь видит общее сообщение, детали уходят только в `console.error`. Секретов в коде этапа нет.
- **Лишнего кода не обнаружено.** Логика разнесена на `validation`, `logs` и `actions` без дублирования, кроме повторяющихся блоков в четырёх add-действиях (допустимо).

## Замечания (по важности)
1. **Средняя. Форма очищается после ошибки валидации.** React 19 сбрасывает неконтролируемую форму после `action`. Пользователь теряет ввод при любой ошибке сервера, например при слишком длинной заметке. Для описания приёма пищи и заметок это неприятно, особенно на телефоне. Решение: вернуть введённые значения в `FormState` и использовать их как `defaultValue`, либо перейти на контролируемые поля.
2. **Средняя. Нет нижней границы даты.** Допустима любая прошлая дата, вплоть до `0000-01-01`. Сейчас это только «мусорные» данные, но на этапе 4 (баллы за записи и серии дней) можно будет накручивать баллы задним числом и портить серии. Нужно решить правило (например, не старше 30–365 дней) до начала этапа 4. Сейчас в плане этого нет.
3. **Низкая. Удаление чужой или несуществующей записи молчит.** Защита работает (чужая запись не удаляется), но обратной связи нет. Для обычного UI достижимо только при гонке или подделке запроса, поэтому на практике безопасно. Запись об отказе в лог (без утечки данных) была бы полезна.
4. **Низкая. Только последние 30 записей, без пагинации и фильтров.** Для MVP приемлемо. Ограничение не видно в UI (нет «показаны последние 30»). Старые записи пока нельзя найти и удалить.
5. **Низкая. Добавление не подтверждается визуально.** `SAVED = { error: undefined }`: при успехе нет сообщения, форма просто очищается, а новая запись появляется в списке ниже. Понятно, но можно добавить «Сохранено».
6. **Низкая. Нет проверки на дубли и на частоту.** Двойной клик защищён `disabled={pending}`, но повторная отправка формы с другого вкладки создаст дубль. Для этапа 4 важно, чтобы баллы не начислялись дважды.
7. **Информационно. Приватность здоровья.** Записи здоровья (вес, сон, заметки), в том числе детей, видны всем членам семьи. Это соответствует плану («данные семьи видны членам семьи»), но стоит явно показать это пользователям в интерфейсе или README и учесть в этапе 6.
8. **Информационно. Порог «+24 часа» по будущему.** Сделан с запасом на часовые пояса, поэтому можно записать «завтра». Это осознанное допущение, оно задокументировано в комментарии.
9. **Информационно. Тесты покрывают библиотеку и действия, но не страницы.** Фильтр по семье проверен на уровне `listFamily*`, а передачу `me.familyId` из страниц тестами не проверяют (только чтение кода: всё верно). Отдельного интеграционного теста «пользователь семьи A не видит записи семьи B» на реальной БД нет, хотя план этого требует в разделе «Проверка».
